# ZK Code Arena 系统应用效果评估与推广研究

## 一、项目背景与目标

### 1.1 项目概述

**项目名称**: ZK Code Arena（仲恺在线刷题平台）
**目标用户**: 仲恺农业工程学院人工智能学院全体师生
**预计用户规模**:
- 教师: 50+ 人
- 学生: 2000+ 人
- 并发峰值: 500+ 人（课程实验时段）

**核心功能**:
1. 在线编程题库（支持 C/C++/Java/Python/Go/JavaScript）
2. 实时代码评测（go-judge 沙箱）
3. AI 智能出题（Multi-Agent 协同生成）
4. 班级管理与作业系统
5. 编程竞赛平台
6. 学习数据分析

### 1.2 建设目标

#### 教学目标
- **提升编程能力**: 通过大量实战练习，提高学生算法与数据结构能力
- **个性化学习**: AI 根据学生水平生成适配题目
- **减轻教师负担**: 自动出题、自动判题、自动统计

#### 技术目标
- **高可用性**: 99.5% 可用率，支持 500+ 并发
- **低延迟**: API 响应 < 100ms，判题 < 5s
- **易用性**: 界面友好，操作简单，学习成本低

#### 推广目标
- **第一阶段（1-2 个月）**: 试点班级（3-5 个班，150 人）
- **第二阶段（3-6 个月）**: 全院推广（所有编程课程）
- **第三阶段（6-12 个月）**: 跨学院推广（计算机学院、软件学院）

## 二、应用场景设计

### 2.1 课堂教学场景

#### 场景 1: 数据结构课程实验
**角色**: 教师 + 60 名学生

**流程**:
1. **课前准备**: 教师使用 AI 生成 5 道链表相关题目（难度：easy → medium）
2. **课堂实验**: 学生在线编写代码，实时提交测试
3. **即时反馈**: 系统自动判题，学生查看错误用例
4. **教师监控**: 实时查看班级提交统计（通过率、平均耗时）
5. **课后分析**: 导出学生成绩，识别薄弱知识点

**预期效果**:
- 教师出题时间从 2 小时降至 5 分钟（**96% 提升**）
- 判题时间从人工批改 3 天降至实时（**100% 提升**）
- 学生练习量从 3 题/周提升至 10 题/周（**233% 提升**）

#### 场景 2: 算法设计课程作业
**角色**: 教师 + 80 名学生

**流程**:
1. **布置作业**: 教师创建作业（5 道题，截止时间 7 天）
2. **学生提交**: 学生在截止前多次提交，系统记录最高分
3. **防作弊**: 代码相似度检测（规划中）
4. **成绩统计**: 自动生成成绩单（Excel 导出）

**预期效果**:
- 作业批改时间从 5 小时降至 0（自动化）
- 学生提交率从 75% 提升至 95%（便捷性提升）
- 抄袭检测准确率 > 90%（规划中）

### 2.2 自主学习场景

#### 场景 3: 学生刷题训练
**角色**: 学生个人

**功能**:
- **题库浏览**: 按难度、标签、通过率筛选
- **每日一题**: 系统推荐每日练习题
- **错题本**: 自动收集错题，支持重做
- **学习曲线**: 可视化展示进步轨迹

**预期效果**:
- 日活跃用户 > 30%（600+ 人）
- 人均刷题量 > 5 题/周
- 学生算法竞赛获奖率提升 20%

### 2.3 竞赛场景

#### 场景 4: 院内编程竞赛
**角色**: 竞赛组织者 + 200 名参赛学生

**流程**:
1. **创建竞赛**: 设置时间、题目、排名规则
2. **实时排行**: 动态更新排行榜（ACM/OI 模式）
3. **封榜机制**: 最后 1 小时封榜，增加悬念
4. **赛后分析**: 题目通过率、代码质量分析

**预期效果**:
- 竞赛组织成本降低 80%（无需现场部署环境）
- 参与人数提升 50%（线上便捷性）
- 实时排名提升竞赛体验

## 六、风险评估与应对

### 6.1 技术风险

#### 风险 1: 系统并发过载
**场景**: 课堂实验时，60 人同时提交代码

**影响**: 判题队列阻塞，响应时间 > 10s

**应对措施**:
- 判题队列扩容（100 → 200 容量）
- 增加 worker 数量（4 → 8）
- 限流保护（3 次/分钟 → 5 次/分钟）
- 弹性扩容（Docker Swarm/K8s）

#### 风险 2: 数据库性能瓶颈
**场景**: 排行榜查询涉及大量聚合计算

**影响**: 查询耗时 > 2s，用户体验差

**应对措施**:
- 预计算 + 定时任务（每 5 分钟更新）
- Redis 缓存（Sorted Set）
- 数据库索引优化
- 读写分离（主从复制）

#### 风险 3: AI 服务不稳定
**场景**: 通义千问 API 限流或故障

**影响**: AI 出题功能不可用

**应对措施**:
- 多模型备份（DeepSeek、Kimi）
- 降级策略（使用题库模板）
- 重试机制（指数退避）
- 用户提示（预计等待时间）

### 6.2 教学风险

#### 风险 4: 教师接受度低
**原因**: 不熟悉新工具，担心增加工作量

**应对措施**:
- 详细培训（录制视频教程）
- 一对一指导（技术支持团队）
- 激励机制（优秀案例奖励）
- 简化操作（一键导入、模板功能）

#### 风险 5: 学生作弊
**场景**: 学生互相抄袭代码

**应对措施**:
- 代码相似度检测（Moss 算法）
- 随机题目顺序（防止对答案）
- 时间限制（限时作业）
- 诚信教育（签署承诺书）

### 6.3 运营风险

#### 风险 6: 用户增长过快
**场景**: 全院推广后，用户从 200 增至 2000

**影响**: 服务器资源不足

**应对措施**:
- 分阶段推广（控制增长速度）
- 资源监控（提前预警）
- 弹性扩容（云服务器）
- 成本预算（提前申请经费）

#### 风险 7: 数据安全
**场景**: 学生代码、成绩数据泄露

**应对措施**:
- 数据加密（传输 + 存储）
- 权限控制（RBAC）
- 定期备份（每日增量 + 每周全量）
- 安全审计（日志审查）
