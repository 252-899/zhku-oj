# OJQuestionGen 提示词改进方案（对比版）

## 1. 背景与目标

当前 `pkg/ai/modules/ojquestiongen` 的提示词存在“要求较宽泛、格式约束不够硬、和解析器预期不完全对齐”的问题，这会直接导致以下现象：

- 题目或测试用例返回中混入解释性文字、Markdown 代码块、注释，导致 JSON 提取或反序列化失败。
- 字段名、字段类型、字段数量不稳定，导致下游解析质量波动。
- 标准代码生成要求为 JSON，但实际消费侧只真正需要代码文本，提示词契约和运行时契约不一致。

本次先不直接修改代码，而是先基于以下三类材料，产出一份可 review 的改进方案：

- 当前模块：`pkg/ai/modules/ojquestiongen/prompts/templates.go`
- 当前解析链路：`pkg/ai/modules/ojquestiongen/agents/*.go`
- 示例项目：`temp/DeepTutor/src/agents/question/prompts/zh/*.yaml`

另外，补充参考了官方提示词规范思路：

- OpenAI Prompt engineering / Structured outputs
- Anthropic Prompting best practices / XML tags

目标不是把提示词写得“更长”，而是让它更像一个可执行的“输出契约”。

## 2. 当前实现的主要问题

### 2.1 题目生成 Prompt 存在系统约束与用户约束不一致的问题

当前 `DefaultQuestionGenInstruction` 写的是“返回 JSON 对象”，但 `BuildQuestionGenUserPrompt` 写的是“返回 JSON 数组”，而 `parseProblems()` 实际上也按数组来解析。

- 提示词位置：`pkg/ai/modules/ojquestiongen/prompts/templates.go`
- 解析位置：`pkg/ai/modules/ojquestiongen/agents/question_gen.go`

这类“提示词内部自相矛盾”会让模型在对象和数组之间摇摆，是当前最明显的格式风险点。

### 2.2 没有把“只输出 JSON”定义成硬约束

目前三类 Prompt 都说明了“返回 JSON”，但缺少下面这些更强的约束：

- 不要输出解释性前言
- 不要输出 Markdown 代码块
- 不要输出注释
- 回复首字符和尾字符必须是什么
- 不要输出除约定字段以外的任何内容

而 `question_gen` 与 `testcase_gen` 的解析器都比较脆弱：

- `parseProblems()` 先做字符串截取，再做 `json.Unmarshal`
- `parseTestCases()` 直接从第一个 `[` 到最后一个 `]` 提取数组

这意味着一旦模型在 JSON 前后多说一句话，或者插入额外括号、注释、示例说明，解析就容易失败。

### 2.3 字段契约不够细，模型不知道哪些字段是“必须稳定”的

当前只列出了字段名，没有继续说明：

- 每个字段的类型
- 哪些字段必填
- `difficulty` 只能是 `easy|medium|hard`
- `hint` 缺失时应该返回空字符串还是省略
- `tags` 至少要有几个
- `description` 虽然允许 Markdown，但本质上仍必须是一个 JSON 字符串
- `count` 必须“恰好”等于请求值，而不是“至少”

缺少这些规则时，模型很容易输出：

- 漏字段
- 枚举值写成中文
- `tags` 变成字符串
- `hint` 变成 `null`
- 生成数量不足或超出

### 2.4 没有正例/反例，模型不知道“错在哪里”

当前模板只有一个非常抽象的返回示例：

```json
[{"title": "...", "description": "...", "input_format": "...", "output_format": "...", "hint": "...", "difficulty": "medium", "tags": ["数组", "循环"]}]
```

这个示例的问题是：

- 过于占位符化，不足以教会模型字段风格
- 没有展示合法 JSON 字符串如何承载描述文本
- 没有展示“错误输出长什么样”
- 没有告诉模型哪些常见行为绝对不允许

示例项目在这方面明显更成熟：它不仅有输出结构，还写了“正确示例 / 错误示例 / 不要生成什么”。

### 2.5 角色定义过于笼统，缺少任务边界

当前三段系统提示词基本都是“你是一个专业助手”，但没有明确说明：

- 你当前只负责什么
- 你不负责什么
- 你不是在和用户聊天
- 你不是在解释提示词
- 你不是在输出审阅意见

示例项目在多个 Prompt 里都强调了任务边界，例如：

- “你现在不是在生成题目”
- “你是在寻找题目生成所需的理论知识”
- “不要透露中间推理；只输出最终 JSON”

这种写法可以显著降低模型跑偏到“解释过程”“补充说明”“帮你分析一下”的概率。

### 2.6 标准代码生成 Prompt 的输出契约和消费方式不匹配

当前标准代码 Prompt 要求返回：

```json
{"code": "程序代码", "language": "编程语言"}
```

但 `parseCode()` 的真实行为是：

- 如果能成功提取 JSON 且有 `code` 字段，就返回 `code`
- 否则直接把整段文本当代码返回

这说明当前运行时真正要的核心产物只是“代码文本”，不是一个 JSON 对象。对代码文本强行套 JSON，反而引入额外失败面：

- 换行需要转义
- 引号需要转义
- 反斜杠需要转义
- 模型容易在 JSON 外再包一个代码块

因此，这一段的改造方向应该和题目生成不同，不能机械地沿用“全都输出 JSON”。

### 2.7 测试用例 Prompt 没有把“覆盖策略”写成结构化要求

当前测试用例 Prompt 只说“覆盖正常/边界/特殊情况”，但没有进一步规定：

- 第 1 组示例用例应该简单、可读、可作为题面样例
- 其余测试用例如何分布
- 每个测试用例输入/输出必须和题意完全一致
- 是否允许多余空格、注释、解释
- 多行输入输出在 JSON 中该如何表示

结果就是测试用例经常会在“格式合法”与“内容可判题”之间摇摆。

## 3. 示例项目里值得借鉴的设计

参考目录：`temp/DeepTutor/src/agents/question/prompts/zh`

### 3.1 角色定义和任务边界分得很清楚

示例项目的 Prompt 不只是写“你是谁”，而是会同时说明：

- 你的职责是什么
- 你的信息来源是什么
- 当前任务是什么
- 当前任务不是什么

例如：

- `generate_agent.yaml` 会说明“基于背景知识生成题目”
- `retrieve_agent.yaml` 会强调“你不是在生成题目，而是在生成检索查询”
- `relevance_analyzer.yaml` 会强调“你是在分析相关性，不是在拒绝题目”

这种设计的价值是：模型知道自己当前只需完成一个窄任务，而不是“顺手多做一点”。

### 3.2 会显式要求“内部推理，但不要输出推理”

示例项目多处采用类似模式：

- 先默默规划
- 不要透露中间推理
- 只输出最终 JSON

这比简单写“请生成结果”更稳，因为它同时满足了两个目标：

- 允许模型在内部组织信息
- 避免把推理过程泄露到结构化输出里

### 3.3 正例和反例都写出来了

示例项目的检索查询 Prompt 有非常典型的设计：

- 正确示例：纯知识点名称
- 错误示例：题目、任务描述、指令
- 明确写出“不要生成”

这类反例在题目生成场景尤其重要，因为模型最常犯的不是“完全不回答”，而是“差一点正确”。

### 3.4 输出格式要求是“强约束”，不是“建议”

示例项目对格式的要求很硬：

- 只返回有效 JSON
- 不要用 Markdown 代码块包装
- 回复必须以 `{` 开始、以 `}` 结束
- 只输出 JSON，不要有其他文字

这正是我们当前模块最缺的部分。

### 3.5 输入内容按区块组织，便于模型理解边界

示例项目会把输入拆成几个明确区块：

- 要求
- 焦点/角度
- 背景知识
- 参考题目

这比把所有信息揉成一段自然语言更利于模型稳定抽取约束。

## 4. 对比结论

| 维度 | 当前 `ojquestiongen` | 示例项目 | 建议改造方向 |
| --- | --- | --- | --- |
| 角色定义 | 只有“专业助手”级别描述 | 明确职责、当前任务、任务边界 | 为每个 Agent 定义单一职责和禁止事项 |
| 输出约束 | 只说“返回 JSON” | 明确“只输出 JSON、不要代码块、起止字符固定” | 把格式约束写成硬规则 |
| 正确示例 | 只有占位符式返回样例 | 有结构样例，也有正反例 | 补充可执行的正例和反例 |
| 错误示例 | 基本没有 | 明确列出不要生成什么 | 增加最常见失败模式反例 |
| 字段规则 | 只列字段名 | 字段、枚举、场景更具体 | 补充类型、默认值、枚举范围 |
| 数量约束 | 有“生成数量”但不够硬 | 常写“恰好 N 个” | 所有数组输出都改成“恰好” |
| 推理外泄控制 | 基本没有 | 明确“内部推理，不输出推理” | 加入隐藏推理约束 |
| 结构化程度 | 大段自然语言说明 | 分块清晰 | 建议使用 Markdown 分节，必要时用伪 XML 包裹动态内容 |

## 5. 针对 `ojquestiongen` 的改造方案

### 5.1 统一的 Prompt 设计原则

后续改 Prompt 时，建议三类 Agent 都遵守同一套结构：

1. `Identity`
   说明你是谁、你服务于什么场景。
2. `Task Boundary`
   明确你当前只负责什么，不负责什么。
3. `Quality Rules`
   描述内容质量要求。
4. `Output Contract`
   严格定义输出格式、起止字符、字段、类型、禁止项。
5. `Examples`
   至少包含一个正确示例和一个错误示例。
6. `Input Blocks`
   用明显标签包住动态输入，例如知识点、难度、额外要求、参考代码等。

建议采用 Markdown 标题或轻量标签分段，例如：

```text
# Identity
# Task Boundary
# Quality Rules
# Output Contract
# Correct Example
# Incorrect Example
# Input
```

如果后续发现多段动态内容容易串味，可以进一步引入伪 XML：

```text
<knowledge_points>...</knowledge_points>
<difficulty>medium</difficulty>
<additional_requirements>...</additional_requirements>
```

这样做的原因也和官方最佳实践一致：结构清晰、边界清晰、示例清晰时，模型更容易稳定遵守格式。

### 5.2 题目生成 Prompt 改造建议

#### 5.2.1 目标

生成可被 OJ 工作流直接消费的题目数组，且数组中的每个对象都能稳定反序列化为：

- `title`
- `description`
- `input_format`
- `output_format`
- `hint`
- `difficulty`
- `tags`

#### 5.2.2 关键改动点

1. 统一规定输出必须是 JSON 数组，不再出现“对象/数组”冲突。
2. 明确“恰好生成 `{count}` 道题”。
3. 明确“只输出 JSON 数组，不要任何额外文字”。
4. 明确“回复第一个字符必须是 `[`，最后一个字符必须是 `]`”。
5. 明确“禁止 Markdown 代码块、禁止注释、禁止尾随逗号、禁止额外字段”。
6. 明确 `difficulty` 只能使用 `easy|medium|hard`。
7. 明确 `hint` 没有内容时返回空字符串 `""`，不要省略、不要返回 `null`。
8. 明确 `tags` 必须是数组。
9. 把“解题思路/算法说明”收敛到 `hint` 字段，不要把完整题解写进 `description`。
10. 明确每道题都要有可判定的输入输出，不允许叙述性开放题。

#### 5.2.3 推荐的正确示例

```json
[
  {
    "title": "校园饮水机排队统计",
    "description": "某教学楼的饮水机前排队人数会在一天内多次变化。现在给定若干时刻的人数变化记录，请你计算最后的排队人数。题目保证任意时刻排队人数不会为负数。",
    "input_format": "第一行输入一个整数 n，表示记录条数。第二行输入 n 个整数，正数表示新增人数，负数表示离开人数。",
    "output_format": "输出一个整数，表示最后的排队人数。",
    "hint": "按照顺序累加变化量即可，注意处理 0 和负数变化。",
    "difficulty": "easy",
    "tags": ["模拟", "数组", "循环"]
  }
]
```

这个示例的价值是：

- 是合法 JSON
- 字段完整
- 值的风格贴近真实 OJ 数据
- 没有多余说明

#### 5.2.4 推荐的错误示例

错误示例 1：多余前言

```text
下面是我为你生成的题目：
[ ... ]
```

错误示例 2：Markdown 代码块

~~~text
```json
[ ... ]
```
~~~

错误示例 3：字段不合法

```json
[
  {
    "title": "题目A",
    "description": "……",
    "difficulty": "中等",
    "tags": "数组"
  }
]
```

错误原因：

- `difficulty` 不是约定枚举
- `tags` 类型错误
- 缺少必填字段

#### 5.2.5 推荐的 Prompt 骨架

```text
# Identity
你是 OJ 编程题生成 Agent，负责生成可以被程序判题系统直接消费的题目草案。

# Task Boundary
- 你只负责生成题目数据。
- 你不是在和用户聊天。
- 你不是在解释提示词。
- 你不是在输出审阅意见。
- 不要输出中间推理，只输出最终结果。

# Quality Rules
- 题目必须有明确场景，但不能牺牲可判题性。
- 输入输出必须确定、唯一、可程序化验证。
- 难度必须与请求一致。
- 每道题必须和其他题目有明显区别，不能只换名字或数字。
- `hint` 提供简洁思路提示，不要写完整题解。

# Output Contract
- 只输出一个 JSON 数组。
- 回复必须以 `[` 开始，以 `]` 结束。
- 数组长度必须恰好等于 {count}。
- 每个元素只能包含以下字段：title, description, input_format, output_format, hint, difficulty, tags。
- `difficulty` 只能是 `easy`、`medium`、`hard`。
- `hint` 没有内容时返回空字符串。
- `tags` 必须是字符串数组。
- 不要输出 Markdown 代码块、注释、解释、前言、额外字段。

# Correct Example
...

# Incorrect Example
...

# Input
<knowledge_points>{knowledge_points}</knowledge_points>
<difficulty>{difficulty}</difficulty>
<languages>{languages}</languages>
<standard_language>{standard_language}</standard_language>
<additional_requirements>{additional_requirements}</additional_requirements>
```

### 5.3 标准代码生成 Prompt 改造建议

#### 5.3.1 结论

这一段不建议继续把“JSON 对象”作为首选输出契约。

原因很简单：当前运行时最终只需要代码文本，而不是一个需要二次提取的 JSON 包装层。对代码使用 JSON，会增加无意义的转义难度。

#### 5.3.2 推荐方向

推荐方案：

- 直接返回纯代码文本
- 不要输出解释
- 不要输出 Markdown 代码块
- 不要在代码前后输出任何其他文字

如果将来确实需要结构化元数据，再结合模型层的结构化输出能力做 `json_schema`，而不是继续靠自由文本拼 JSON。

#### 5.3.3 推荐的正确示例

```text
import sys

def main():
    data = list(map(int, sys.stdin.read().strip().split()))
    if not data:
        return
    n = data[0]
    nums = data[1:1+n]
    print(sum(nums))

if __name__ == "__main__":
    main()
```

#### 5.3.4 推荐的错误示例

错误示例 1：带解释

```text
下面是 Python 解法：
import sys
...
```

错误示例 2：代码块包装

~~~text
```python
import sys
...
```
~~~

错误示例 3：继续强制 JSON

```json
{"code": "import sys\nprint(1)", "language": "python"}
```

该示例不是“绝对错误”，但在当前模块里不是最优输出契约，因为它增加了额外转义成本，却没有带来消费收益。

#### 5.3.5 推荐的 Prompt 骨架

```text
# Identity
你是 OJ 标准程序生成 Agent，负责输出能够通过题目测试的标准答案代码。

# Task Boundary
- 你只输出代码。
- 你不是在解释思路。
- 你不是在输出测试说明。
- 不要输出中间推理。

# Quality Rules
- 必须严格符合题目输入输出格式。
- 必须处理边界情况。
- 必须使用指定编程语言。
- 只使用标准输入和标准输出。

# Output Contract
- 只返回源码文本。
- 回复第一行必须就是代码，不要有任何前言。
- 不要使用 Markdown 代码块。
- 不要输出解释、注释性说明、JSON 包装。

# Correct Example
...

# Incorrect Example
...

# Input
<problem_title>{title}</problem_title>
<problem_description>{description}</problem_description>
<input_format>{input_format}</input_format>
<output_format>{output_format}</output_format>
<language>{language}</language>
```

### 5.4 测试用例生成 Prompt 改造建议

#### 5.4.1 目标

稳定输出可直接反序列化、可直接用于判题验证的测试用例数组。

#### 5.4.2 关键改动点

1. 强制输出 JSON 数组。
2. 明确数组长度必须恰好等于 `count`。
3. 明确第一个测试用例必须是简单、可读的示例用例，且 `is_sample=true`。
4. 明确其余测试用例应覆盖普通、边界、特殊场景。
5. 明确每个元素只允许 `input`、`expected_output`、`is_sample`。
6. 明确多行输入输出必须作为合法 JSON 字符串返回，换行使用 `\n`。
7. 明确不要输出解释文字、用例分析、编号说明。

#### 5.4.3 推荐的正确示例

```json
[
  {
    "input": "5\n1 2 3 4 5\n",
    "expected_output": "15\n",
    "is_sample": true
  },
  {
    "input": "1\n0\n",
    "expected_output": "0\n",
    "is_sample": false
  },
  {
    "input": "4\n10 -3 5 -2\n",
    "expected_output": "10\n",
    "is_sample": false
  }
]
```

#### 5.4.4 推荐的错误示例

错误示例 1：把解释混在数组外

```text
第一个是样例，后面是边界测试：
[ ... ]
```

错误示例 2：`input` 写成数组

```json
[
  {
    "input": [1, 2, 3],
    "expected_output": "6",
    "is_sample": true
  }
]
```

错误示例 3：多行字符串不是合法 JSON 字符串

```text
[
  {
    "input": "5
1 2 3 4 5",
    "expected_output": "15",
    "is_sample": true
  }
]
```

上面这种写法在很多情况下不是合法 JSON，应明确要求用 `\n` 转义换行。

#### 5.4.5 推荐的 Prompt 骨架

```text
# Identity
你是 OJ 测试用例生成 Agent，负责生成可直接用于程序判题的测试数据。

# Task Boundary
- 你只输出测试用例数组。
- 你不是在解释测试策略。
- 你不是在输出题解。
- 不要输出中间推理。

# Quality Rules
- 所有测试用例都必须与题意和标准程序一致。
- 第 1 组必须是简单、清晰、可作为样例展示的用例。
- 其余用例需要覆盖普通情况、边界情况、特殊情况。
- 生成数量必须恰好等于 {count}。

# Output Contract
- 只输出一个 JSON 数组。
- 回复必须以 `[` 开始，以 `]` 结束。
- 每个元素只能包含 input、expected_output、is_sample。
- input 和 expected_output 必须是字符串。
- 多行内容必须使用 `\n`。
- 不要输出解释、编号、注释、Markdown 代码块。

# Correct Example
...

# Incorrect Example
...

# Input
<problem_title>{title}</problem_title>
<problem_description>{description}</problem_description>
<input_format>{input_format}</input_format>
<output_format>{output_format}</output_format>
<standard_code>{standard_code}</standard_code>
```

## 6. 建议的实施顺序

后续真正动手改 Prompt 时，建议按下面顺序推进：

1. 先改 `QuestionGenPrompt`
   先统一数组契约、字段契约、正反例、只输出 JSON 约束。
2. 再改 `TestcaseGenPrompt`
   因为它和 `question_gen` 一样，对 JSON 结构稳定性要求很高。
3. 最后改 `StandardCodeGenPrompt`
   这里建议顺手把“输出 JSON”改成“输出纯代码”。

这样做的收益是最大、风险也最可控。

## 7. 附加工程建议（非本次 Prompt 文案修改范围）

虽然这次先只讨论提示词，但有几项工程措施会明显提升整体稳定性：

### 7.1 增加输出校验与重试

在 `question_gen` 和 `testcase_gen` 中，可在解析失败后增加一次“格式修复重试”：

- 把解析错误反馈给模型
- 明确要求仅修复格式，不重写内容

这通常比第一次就把提示词写得非常长更划算。

### 7.2 将 Prompt 契约和 Go 结构体保持严格一致

建议未来把字段约束显式和这些结构体绑定：

- `GeneratedProblem`
- `TestCase`

避免出现“Prompt 说对象，代码要数组”“Prompt 允许省略，代码却要求必填”这类偏差。

### 7.3 如果底层 LLM 接入后续支持结构化输出，优先用 Schema

当前 `pkg/ai/infra/llm/factory.go` 只是普通 `Generate()`，还没有显式暴露 `response_format/json_schema` 能力。

如果后续基础设施支持，建议优先做：

- 题目生成：JSON Schema
- 测试用例生成：JSON Schema

OpenAI 官方文档也明确建议：如果可以使用 Structured Outputs，就优先使用，而不是只依赖“请返回 JSON”的自然语言约束。

### 7.4 代码生成建议保留为“纯代码输出”

即使未来题目和测试用例改为 Schema 输出，我仍建议标准代码生成默认保留为“纯代码文本”，除非业务真的需要附加字段。

原因是代码天然更适合直接消费，不适合包在一个自由文本 JSON 字符串里。

## 8. 最终建议结论

对于 `pkg/ai/modules/ojquestiongen`，后续 Prompt 改造建议遵循以下原则：

- 题目生成和测试用例生成走“强结构化 JSON 契约”路线。
- 标准代码生成走“纯代码文本”路线。
- 三类 Prompt 都要补上：角色定义、任务边界、输出硬约束、正确示例、错误示例。
- 所有数组输出都用“恰好 N 个”，不要用模糊表述。
- 所有结构化输出都必须写明：只输出结果，不要前言，不要 Markdown，不要解释。

一句话总结：

当前 Prompt 的主要问题不是“不够详细”，而是“不够像契约”；后续要把它从“生成建议”升级成“可执行输出规范”。
